# プログラミング 自己完結 150本

プログラミングの基礎（変数、配列、ループ、関数、条件分岐）は既知として、**1本だけ見て閉じる**動画の目次です。
`project/curriculum_algorithm_200/`（教科書順の200本）とは別シリーズです。統合しない。番号も混ぜない。数学150本とも番号を混ぜない。

## 視聴契約

- **前提**: 高校数学と、初級プログラミング。ビッグOやグラフ理論は知らない前提でよい。必要ならその本の中で導入する。
- **自己完結**: シリーズ内の別の回を見ていなくても理解できる。「先に #n を見ること」は要求しない。
- **1本の単位**: データ構造名や算法名ではなく、具体的な問い。
- **物語**: 問い → 素朴な試行（遅さ・破綻を残す）→ 工夫して解く → 一般化（算法・データ構造・計算量の型）→ まとめ。
- **尺**: 5〜12分目安。状態の変化を飛ばさない。目標尺に合わせる空白は置かない。読み時間と画面のポーズは初学者向けに取る。日本語は省略しすぎない。
- **制作**: Manim、日本語。先に `storyboard.md`、そのあと `scene.py`。基底は `LessonScene`。擬似コードと図を並置してよい。既存の可視化コードは流用してよい。

グループ分けはプレイリスト用であり、視聴順ではない。どの番号から見てもよい。#131以降のような高度な題材（計算理論、システム）も、実装の細部ではなく1つの具体例で成立する直感を、自己完結に見せる。

## 1本の型

| パート | 内容 |
|---|---|
| 問い | 具体的で、コンピュータに解かせたくなる問題。答えはすぐ出さない。 |
| 試行 | 素朴な方法を最後まで走らせ、遅さや見落としを見せる。 |
| 工夫 | 観察して手順や持ち方を変える。途中の状態は残す。 |
| 一般化 | 「今やったことは、〇〇という算法／構造だった」 |
| まとめ | 持ち帰れる型だけ。次回必見にはしない。末尾の補足は、いま一般化した事柄の応用例や豆知識に限る。なくてもよい。 |

コードは削除しない。既存の配列・木・探索の動きは、試行や工夫のパートの素材にしてよい。

## 各本

### 探す・覚える・履歴

### 1. 巨大なリストに同じ値が 2 つあるか
- **slug:** `001_find_duplicate`
- **問い:** 長さ \(n\) の配列に、同じ値が 2 回以上出るかを知りたい。\(n\) が 100 万でも間に合う持ち方はあるか。
- **試行:** 全てのペアを比べる。\(n=4\) なら 6 回で足りるが、\(n\) が倍になると仕事は約 4 倍。見終わった値を印の箱に置くと、一回ずつ見るだけで足りる。
- **一般化:** ハッシュ表（または値の範囲が小さいときの印配列）。時間と追加メモリのトレードオフ。仕事の増え方を \(O(n)\) と \(O(n^2)\) で書く。
- **仮定:** 配列とループ。ハッシュの内部は「値から箱の番号を決める」まで。ビッグOはこの本で「増え方の型」として導入してよい。

### 2. 足して目標になる 2 数はあるか
- **slug:** `002_two_sum`
- **問い:** 配列の中から、和が指定の数 \(S\) になる 2 元を見つけたい。全部のペアを見ずに済むか。
- **試行:** 二重ループ。ソートして小さい端と大きい端から迫る。片側を見たあと、\(S-x\) が既に出たか覚える。
- **一般化:** ハッシュで補数を引く。ソート＋ツーポインタ。前処理で問いの形を変える、という型。
- **仮定:** 配列。ソートは「並べ替えたあと隣や両端が使える」として使ってよい（実装の詳細は別問い）。

### 3. エディタの取り消しはどう持つか
- **slug:** `003_undo_stack`
- **問い:** 文字を足したり消したりしたあと、取り消すと直前の状態に戻したい。戻した操作をやり直しもしたい。どこに何を積むか。
- **試行:** 全文のコピーを毎回残すとメモリが膨らむ。履歴を配列の途中に差し込むと、古い順と新しい順が崩れる。
- **一般化:** スタック（LIFO）。undo 用と redo 用の 2 本。最後に入れたものを先に出す構造は、括弧や関数呼び出しにも出るが、この本は履歴で閉じる。
- **仮定:** 配列の末尾への追加と削除。

### 4. 印刷ジョブの順番
- **slug:** `004_print_queue`
- **問い:** 先に頼んだ印刷から出したい。新しい依頼は後ろへ、機械が空いたら前から取りたい。先頭の削除を配列でやると何が辛いか。
- **試行:** 配列の先頭を消すたびに残りをずらす。末尾だけ触るリスト、または頭と尾の添字を進める環状バッファ。
- **一般化:** キュー（FIFO）。待ち行列。BFS の「次に見る」も同じ型だが、この本は印刷で閉じる。
- **仮定:** 配列。ポインタや添字。

### 5. 括弧は正しく閉じているか
- **slug:** `005_brackets_match`
- **問い:** `()[]{}` が混ざった列が、正しく対応しているかを左から一回で決めたい。数え上げのプラスマイナスだけでは足りない例は何か。

### 8. 比較だけで並べるとき何回は必要か
- **slug:** `008_sorting_lower_bound`
- **問い:** \(n\) 枚のカードを、大小比較だけを使って並べ替える。どんな手順でも、最悪でだいたい何回は比較が必要か。なぜ \(n\) 回では足りないか。
- **試行:** 隣同士を入れ替える（バブル）と約 \(n^2\)。もっと上手い手順でも、結果は \(n!\) 通りある。比較一回は二股にしか分かれない。
- **一般化:** 決定木の高さは少なくとも \(\log_2(n!)\)。スターリングで \(\Theta(n\log n)\)。比較ソートの下限。計数ソートなど「比較以外」は別ルール。
- **仮定:** 階乗。対数。ビッグOはこの本で「下からも同じ型」として出してよい。

### 9. バラバラな列を速く並べたい
- **slug:** `009_quicksort_random`

- **試行:** 既にソート済みで端を境にすると、片側が空に近く、仕事が \(n^2\) に近い。境をランダムにすると、偏りが続きにくい。
- **一般化:** クイックソート。平均 \(\Theta(n\log n)\)、最悪 \(O(n^2)\)。乱択が最悪を稀にする。分割統治。
- **仮定:** 配列の入れ替え。再帰は「同じ手順を短い区間へ」として導入してよい。

### 10. 同じ値の順序を崩さず半分に分ける

### 11. トランプを偏りなく混ぜる

- **仮定:** 乱数のつもりで「等確率な整数」。剰余バイアスは短く触れてよい。

### 37. なぜ連続した配列の走査が速いか
- **slug:** `037_array_vs_linked_list`

- **仮定:** 配列とポインタの絵。機械語は出さず、「近くの箱は一緒に届く」でよい。

### 38. 一番急ぎの仕事を繰り返す
- **slug:** `038_heap_priority`
- **問い:** 仕事が随時追加され、毎回「今いちばん優先度が高いもの」だけ取りたい。ソートし直すと何が辛いか。二分木の親が子より急、を保つには。

### 39. 区間の合計を何度も聞かれる
- **slug:** `039_prefix_sums`

- **一般化:** 型検査の直感。プログラムを実際に動かさずに、式の構造だけから矛盾を見つける（静的解析の一種）。
- **仮定:** #68 の構文木の考え方を本編で再導入。

### 140. プログラムの実行を一歩ずつ再現するには何を記録すればよいか
- **slug:** `140_deterministic_replay_debugging`
- **問い:** 「たまにしか起きない」バグを再現するのが難しいとき、1回の実行を完全に記録して、あとで正確に再生する（デバッガでコマ送りする）にはどうすればよいか。
- **試行:** プログラムの実行結果を左右する要素（乱数、外部からの入力の到着順序、#121のような並行処理の順序）を書き出す。これらをすべて記録しておけば、再生時に同じ順序を強制できることに気づく。
- **一般化:** 決定的実行とログ（デターミニスティック・リプレイ）。「実行結果を左右する不確定要素」を特定し、記録・再生することでデバッグを可能にする。
- **仮定:** #121 のような非決定性の原因を本編で再導入。

### 141. 少ないデータで新しい写真を分類するには何を数えればいいか
- **slug:** `141_k_nearest_neighbors`
- **問い:** 「これは猫か犬か」を判定するのに、複雑な学習をせず、過去に見た写真との「近さ」だけで決められるか。
- **試行:** #42のボロノイ図の考え方のように、新しいデータ点に一番近い既存のデータのラベルをそのまま採用する。1点だけでなく、近い複数点の多数決にすると、どう結果が変わるかを試す。
- **一般化:** k近傍法（k-NN）。#42, #108（距離・類似度）の考え方をそのまま分類問題に応用する、最も単純な学習アルゴリズムの1つ。

### 142. 「木」をたくさん集めて多数決すると精度が上がるのはなぜか
- **slug:** `142_random_forest_voting`
- **問い:** 1本の決定木（#20のような分岐の繰り返しで分類する木）は間違えやすいことがある。同じデータから複数の木を作って多数決させると、なぜ精度が上がることが多いのか。
- **試行:** 同じデータの一部だけをランダムに使って複数の木を作る（それぞれ少し違う木になる）。1本ずつの判定と、複数の木の多数決の結果を比較する。
- **一般化:** ランダムフォレスト。個々には間違えやすい判定でも、独立性のある複数の判定を集めると、誤りが打ち消し合って全体の精度が上がる（数学150本の#12の中心極限の考え方の応用）。
- **仮定:** 決定木の分岐の考え方、多数決。

### 143. スパムメールをどうやって自動で見分けるか
- **slug:** `143_naive_bayes_spam`
- **問い:** メールの本文に含まれる単語だけから、スパムかどうかを判定したい。「無料」「当選」のような単語がスパムに多いことをどう数値的に使うか。
- **試行:** 数学150本の#11（ベイズの定理）の考え方で、「この単語を含むメールがスパムである確率」を、過去のメールから計算する。複数の単語の情報を、独立と仮定して掛け合わせてみる。
- **一般化:** ナイーブベイズ分類。各単語の出現を（本当は独立でなくても）独立と仮定して掛け合わせる、という簡略化が驚くほど実用的に効く。数学150本の#80（独立性の仮定の危うさ）とのバランスも触れる。
- **仮定:** 数学150本の#11, #80 の考え方を本編で再導入。

### 144. おすすめ商品はどうやって「似ている人」を見つけて決まるのか

- **試行:** 各利用者の購入履歴を、商品ごとに0/1（買った・買っていない）を並べたベクトルとして表す。#108のコサイン類似度で利用者どうしの近さを測ってみる。

### 145. 画像の中の輪郭やパターンをどう機械的に取り出すか
- **slug:** `145_convolution_intuition`
- **問い:** 画像の中の「縦線」や「輪郭」を、人が見なくてもプログラムに検出させたい。小さな数字の格子（フィルタ）を画像に重ねて滑らせると、なぜそれが可能になるのか。
- **試行:** 小さな数字の格子（例えば縦線を強調する格子）を、画像の一部分に重ねて、対応する画素の値を掛けて合計する操作を、具体的な数値の画像で試す。格子を右へ1つずらして、同じ操作を繰り返す。
- **一般化:** 畳み込み（convolution）の直感。決まった小さいパターンとの「一致度」を、画像全体を滑らせて計算することで、特徴（輪郭など）を検出できる。
- **仮定:** 行列（格子状の数の配列）の要素ごとの掛け算と合計。

### 146. ニューラルネットワークの「学習」は何を繰り返しているのか
- **slug:** `146_backpropagation_intuition`
- **問い:** ニューラルネットワークが「正解」を出すように調整されていく過程で、内部のたくさんの数（重み）はどうやって少しずつ直されているのか。
- **試行:** #44の勾配降下（誤差を減らす方向へ動く）の考え方を、1層だけの単純なネットワークに当てはめてみる。層が複数になると、それぞれの重みが誤差にどう影響しているかを、直接計算するのが大変になることに気づく。
- **一般化:** 誤差逆伝播（バックプロパゲーション）の直感。出力側の誤差を、層をさかのぼって「どの重みがどれだけ誤差に責任があるか」に分配していく（連鎖律の直感）。
- **仮定:** #44 の勾配降下を本編で再導入。

### 147. ゲームを繰り返しプレイして強くなるアルゴリズムはどう学ぶか

- **一般化:** 強化学習の初歩（試行と報酬）。#118のシミュレーションと、#146の「結果から少しずつ直す」考え方を組み合わせた学習の枠組み。
- **仮定:** #118, #146 を本編で再導入。

### 148. 情報を圧縮すればするほど、なぜ復元できなくなる限界があるのか
- **slug:** `148_shannon_limit_intuition`

- **試行:** 数学150本の#45（エントロピー、情報量）の考え方を思い出し、ある文章の「予測しにくさ」そのものが、圧縮できる限界を決めていることに気づく。極端に単純な文章と、ランダムな文章で圧縮率がどう変わるかを比べる。
- **一般化:** シャノンの限界。情報源のエントロピー以下には（平均的に）圧縮できない、という理論的下限。#17のハフマン符号がこの限界にどれだけ近づけるかという評価。

### 149. アルゴリズムの良さを実行時間以外でどう測るか

### 150. 同じに見える2つの問題で、なぜ片方は貪欲で解けもう片方はDPが要るのか
- **slug:** `150_greedy_vs_dp_when_to_choose`
- **問い:** #28（区間スケジューリング、貪欲で解ける）と#30（ナップサック、貪欲では解けずDPが要る）は、どちらも「いくつかの候補から選ぶ」問題に見える。この2つの違いは、問題のどんな性質から来るのか。
- **試行:** #28では「終了が一番早いものを選んでも、残りの選択の余地が最大限残る」ことを確認する。#30では「価値密度が一番高い荷物を選んでも、残りの容量の使い方に無駄が出る例」を具体的に作り、#28との違いを比べる。
- **一般化:** 貪欲法が使えるのは「一度の最良の選択が、常に何らかの最適解に含まれる」性質（#91のマトロイド直感）を持つ問題。それが無い（今の選択が将来の可能性を複雑に変える）場合は、#29や#30のように部分問題の答えを表に持つDPが必要になる。この見分け方が、アルゴリズム設計の最初の判断になる。
- **仮定:** #28, #29, #30, #91 の考え方を本編で再導入。
